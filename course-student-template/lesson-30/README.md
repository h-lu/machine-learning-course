# 第 30 课（S28）：更高效果值得多少等待和计算

## 本课要解决什么问题

同一个设备服务台助手现在有 `fast` 和 `thorough` 两种本地处理方案。后者能识别更多说法，但计算次数更多。重复请求还可以读取缓存。你要在同一批 10 条请求上比较正确数、本机实际耗时、配置给出的成本估算和缓存命中。

**第一次做时从 [入门支持](SUPPORT.md) 开始。** 本课把三类量分开保存：路线正确数是程序实际结果，`timings.csv` 是本机实际测得的本地计算耗时，`estimated_cost_units` 是按配置单价计算的估算值。缓存命中耗时不能称为新的模型推理耗时。本课程序是本地确定性路由，不是大模型。

## 本课要学会什么

| 标准术语 | 本课需要掌握的含义 |
|---|---|
| 质量（quality） | 本课用路线正确数除以 10 表示，只覆盖给定请求。 |
| 延迟（latency） | 从开始处理到得到结果的时间；必须说明测量环境和测量对象。 |
| 成本估算（cost estimate） | 用配置单价乘新计算次数得到的比较量，不是真实账单。 |
| 缓存（cache） | 对规范化后相同的输入和同一方案复用已保存结果；配置改变后不能继续当作同一结果。 |
| 重复测量（repeated measurement） | 在相同条件下多次计时，用来观察波动，不增加独立评价请求数。 |

完成后，你应该能按预算选择方案，并把质量、实际耗时和估算成本分别报告。

## 90 分钟安排

| 时间 | 活动 |
|---|---|
| 0–15 分钟 | 区分评价请求数、计时重复次数和缓存命中次数 |
| 15–35 分钟 | 运行三次计时起点，核对 8/10 与 10/10 |
| 35–52 分钟 | 运行五次计时，比较波动而不扩大质量分母 |
| 52–68 分钟 | 改一条重复输入，再按预算或等待上限检查建议 |
| 68–75 分钟 | 写质量、等待、估算成本和采用条件 |
| 75–90 分钟 | 完成 A 版概念检查、AI 学习、B 版检查并提交 |

## 完成步骤

1. 从仓库根目录运行起点：

   ```bash
   python scripts/course.py start 30
   python lesson-30/analysis.py --config lesson-30/config-start.json --output lesson-30/artifacts/start
   ```

2. 打开 `summary.json`。手算无缓存时 `fast` 为 `8/10=0.80`，`thorough` 为 `10/10=1.00`。再核对开启缓存后正确数不变；缓存只减少规范化后相同输入的新计算次数。
3. 打开 `timings.csv`，比较同一方案的六项信息：`total_elapsed_ms` 是处理这批 10 条请求的本机实测总耗时，`mean_request_latency_ms` 是总耗时除以 10 得到的平均每条延迟。`fresh_compute_ms` 只累加新计算环节，`cache_lookup_ms` 只累加缓存查询环节，`fresh_calls` 与 `cache_hits` 是计数。这些耗时字段的单位都是毫秒。计时会波动，质量分母仍是 10 条请求，不是重复次数乘 10。
4. 先预计把计时从 3 次增加到 5 次会改变哪些量，再运行：

   ```bash
   python lesson-30/analysis.py --config lesson-30/config-support.json --output lesson-30/artifacts/support
   ```

   它增加对波动的观察，不创造新的质量样本。
5. 把现成的 `config-check.json` 复制为 `config.json`，再编辑其中的 `repeat_input_check`。你可选 P05 或 P08；把 `replacement_text` 写成与它原先重复的那条请求不同、但参考路线仍一致的新文字。先预计缓存命中会怎样变，再运行 `python scripts/course.py run 30`。打开 `changed_records.csv` 和 `summary.json` 的 `repeat_input_check`，检查实际变化。最后给出一个明确预算或允许等待上限，从四个方案中选择并说明理由。

   ```json
   "repeat_input_check": {
     "id": "P05",
     "replacement_text": "学生设备最长可以借几天？"
   }
   ```

## 必须提交什么

- 最终配置、可重跑的 `summary.json`、`records.csv` 和 `changed_records.csv`，以及本次机器生成的 `timings.csv`。
- `8/10` 与 `10/10` 的手算及一个缓存成本估算，例如 8 次新计算乘单价 1 等于 8 个估算单位。
- 至少三次实际计时的最小值、最大值和测量环境说明。
- 一个已实际运行的重复输入变化检查，以及在明确预算或等待上限下采用 `fast`、`thorough`、缓存或不采用的理由。
- 明确说明哪些是实测、哪些是估算、哪些是缓存重放。

`timings.csv` 每次运行都会变化，因此提交检查只对确定性的 `summary.json`、`records.csv` 和 `changed_records.csv` 做逐字节重跑核对；仍需把本次 `timings.csv` 与报告一起提交供人工核对。`course.py check` 通过不代表计时文件已经进入 Git，提交后还要在 Gitea 的本课目录中确认它确实可见。

`artifacts/` 默认被 Git 忽略。按通用提交指南暂存确定性结果后，再明确加入本次计时文件：

```bash
git add -f lesson-30/artifacts/timings.csv
```

## 不同起点怎么做

### 入门支持（Support）：先核对一个正确率和一次缓存命中

按 [SUPPORT.md](SUPPORT.md) 运行现成配置，找到 P05 的缓存命中，再计算 8/10。使用支持路径不降低完成标准。

### 必做任务（Core）：在同一任务上比较质量、耗时和估算成本

所有人都要完成重复计时、缓存比较、一项已运行的输入变化，并在自己写明的预算或等待上限下作选择。

### 提高任务（Upgrade）：画出可接受方案集合

找出不存在另一个方案同时质量更高、耗时更低且估算成本更低的方案，并解释取舍。

### 换数据重测（Transfer）：改变重复比例

只改变重复请求数量，比较缓存命中和新计算次数；不要把重放速度写成新输入处理速度。

### 自选拓展（Open extension）：记录另一台机器

在另一台机器重复同一配置，分别报告环境和波动，不合并成一个“通用延迟”。

## 运行限制

计时对象是课程中的本地哈希计算和路由程序，不是神经网络或在线模型推理。成本单位是人为给定的比较尺度。普通 CPU 数秒内完成；后台负载会影响实际计时。
