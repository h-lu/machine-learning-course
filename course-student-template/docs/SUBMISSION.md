# 把实验交给别人检查

通常只需要编辑三份说明文件。程序、模型和报告都可以自行组织；如果换了位置，在提交清单里写清楚。

| 文件 | 用来做什么 |
|---|---|
| `contract.json` | 任务说明（task specification）：写问题、使用者、数据来源、主要指标、怎样分开开发和测试，以及预计结果 |
| `report.md` | 解释你作了什么选择、结果和预计哪里不同、自己设计的检查发现了什么、现在建议怎样做 |
| `submission.json` | 告诉别人当前进度、怎样运行、报告和结果放在哪里 |

字段名是程序读取的输入接口约定（input schema）。`question` 是你要回答的问题；`user` 是谁会使用结果；`data_source` 是数据来源；`metric` 是主要指标及理由；`split_plan` 是评价数据的安排；`initial_expectation` 是实验前预计结果。文字长短不限，可以在字段里引用报告的相关段落。

## 完成一次提交

1. 开始时把 `status` 从 `not_started` 改为 `in_progress`，填写任务说明。不要先看结果再写成事前预计。
2. 运行起步程序，作出自己的选择，再完成一个合理比较。把结果文件与运行方法记下来。
3. 设计一条容易让模型出错的输入，或换一种影响用途的条件。核对实际输出；保留支持和不支持原判断的结果。
4. 写报告。说明主要指标的分母，至少具体讲清一个样本或一段计算，再写出继续使用、修改后重试或停止使用的理由。
5. 在新输出目录重新运行，核对主要结果。更新 `run`、`report`、`artifacts`；完成本课要求后，将状态改成 `complete`。

例如，从仓库根目录运行 C02，输出到新目录：

```bash
python3 lesson-02/analysis.py --output /tmp/ml-c02-rerun
```

它检验程序不依赖上一次的输出。正式整理时，还应在新建虚拟环境或新的仓库副本中按同样命令重跑；安装环境放在课前完成。时间或安装条件不允许时，报告中说明验证到哪一步，不能把同一环境重跑称为已验证全部环境。

`run` 从仓库根目录执行，可以指向你新写的脚本。`report` 和 `artifacts` 填仓库内的相对路径。不要把临时目录写成最终提交路径；把要交的结果放回项目中。

如果教师要求核对课堂概念检查，可在报告末或提交清单中附上 ml-check 生成的 A、B 匿名凭据链接。凭据只证明某轮题目已提交，不证明项目结论正确；不要把凭据当作结果文件。

模板默认忽略 `artifacts/` 中反复生成的示例结果。用 Git 提交正式结果时，可以改放到 `results/` 并更新清单，或明确添加选定文件，例如 `git add -f lesson-02/artifacts/summary.json`。提交前确认需要别人读取的结果确实包含在仓库中。

## 检查通过意味着什么

格式工具检查文件、字段和路径。它不评价你应选哪个模型，也不会根据某个固定分数宣布你的建议正确。入门模板可以通过材料结构检查，但它仍是未完成的模板。教师还会阅读你的比较、失败案例和结论依据。

概念练习用来发现理解上的问题，不替代项目。先作判断，再用 AI 学习，最后换一个情境检验自己是否理解。当前课堂服务按 Gitea 登录账号记录 A/B 作答和学习完成情况，不要求另交匿名凭据。按教师指定的版本和场次参与；完成记录不自动替项目评分，详见[概念检查说明](KNOWLEDGE_CHECK.md)。
