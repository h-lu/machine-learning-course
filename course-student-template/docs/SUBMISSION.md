# 把实验交给别人检查

提交说明集中在三份文件中；研究程序和结果也要一起保存。程序、模型和报告都可以自行组织；如果换了位置，在 `submission.json` 中写清楚。

| 文件 | 用来做什么 |
|---|---|
| `contract.json` | 任务说明（task specification）：写问题、使用者、数据来源、主要指标、怎样分开开发和测试，以及预计结果 |
| `report.md` | 解释你作了什么选择、结果和预计哪里不同、自己设计的检查发现了什么、现在建议怎样做 |
| `submission.json` | 告诉别人当前进度、怎样运行、报告和结果放在哪里 |

这些字段名供程序识别，请保留名称，只修改字段中的内容。`question` 是你要回答的问题；`user` 是谁会使用结果；`data_source` 是数据来源；`metric` 是主要指标、单位、计算办法及选择理由；`split_plan` 是训练、选择方案和最后评价各用哪些数据；`initial_expectation` 是看结果前的预计。文字长短不限，可以在字段里引用报告的相关段落。

## 整理一次提交

下面列出整理作品时需要保存的内容；研究的具体做法和安排由你决定，以本课要求为准。

1. 开始时在 `submission.json` 中把 `status` 从 `not_started` 改为 `in_progress`，填写任务说明。不要先看结果再写成事前预计。
2. 运行起步程序，作出自己的选择，再完成一个合理比较。把结果文件与运行方法记下来。
3. 围绕自己选择的用途，设计一个可能暴露方案限制的输入，或改变一个会影响实际使用的条件。核对实际输出；保留支持和不支持原判断的结果。
4. 写报告。说明主要指标的计算方法、单位和评价数据范围；平均值或比例还要写清分母。至少具体讲清一个样本或一段计算，再写出继续使用、修改后重试或停止使用的理由。
5. 在新输出目录重新运行，核对主要结果。更新 `run`、`report`、`artifacts`；完成本课要求后，将状态改成 `complete`。

例如，从学生仓库根目录运行第02课（C02）的数据起点，输出到仓库内尚不存在的新目录：

```bash
python3 lesson-02/analysis.py --output lesson-02/artifacts/rerun-1
```

再次运行时换成 `rerun-2` 等新目录名。这个例子检查数据起点能否从头运行；自己的研究程序也需要按实际命令重跑。在新建虚拟环境或新的仓库副本中重跑，可以进一步检查依赖和文件是否齐全；安装环境放在课前完成。条件不允许时，报告中说明已经验证到哪一步。

`run` 是命令参数的列表，启动命令、脚本路径和每个参数分别写成一个元素。上面的命令写成 JSON 列表就是 `["python3", "lesson-02/analysis.py", "--output", "lesson-02/artifacts/rerun-1"]`。如果把这次运行的结果用于提交，`artifacts` 也要填写该目录中实际生成的文件路径。命令从学生仓库根目录执行，可以指向你新写的脚本。`report` 和 `artifacts` 填仓库内的相对路径。完整 JSON 示例见[提交流程](WORKFLOW.md)。

项目报告、程序和结果通过个人仓库提交。课堂概念检查按教师指定的 ml-check 场次在线完成，系统按 Gitea 登录账号记录 A/B 作答和学习完成情况，不要求另交匿名凭据。概念检查完成记录不能作为项目结果文件，具体见[概念检查说明](KNOWLEDGE_CHECK.md)。

模板默认忽略 `artifacts/` 中反复生成的结果。用 Git 提交正式结果时，可以改放到 `results/` 并更新清单，或明确添加选定文件。以上面的输出路径为例，添加其中的文件可用 `git add -f lesson-02/artifacts/rerun-1/summary.json`；这只是文件添加示例，默认数据起点不代表完成项目。提交前确认需要别人读取的结果确实包含在仓库中。

## 检查通过意味着什么

本地 `course.py check` 核对提交状态、文件、字段和路径，不评价你应选哪个模型，也不会根据某个固定分数宣布你的建议正确。模板中的字段即使格式正确，也不代表完成；`check` 仍要求完成声明和实际文件。教师还会阅读你的比较、失败案例和结论依据。

概念练习用来发现理解上的问题，不替代项目。先作判断，再用 AI 学习，最后换一个情境检验自己是否理解。按教师指定的版本和场次参与；完成概念检查不等于完成本课项目。
