# 第 04 课 · 记录下来的结果就是好标签吗

## 本课要解决什么问题

维护团队想从历史记录中识别需要优先处理的对象。文件里的“已处理”“发生故障”和“用户投诉”可能描述不同事情；最新记录还可能没有等到结果。你要评估一种标签能否支持你选定的用途，并生成可重跑的标签检查。

请交标签含义、可用记录的选择办法、实际检查结果和使用建议。如果标签暂不可信，提交限制使用或补采数据的方案，同时保留支持判断的计算。

开始前先写清楚四句话：谁会使用结果？输入在什么时候能得到？程序输出什么？结果变差时怎么办？这四句话会帮助你选择评价方法，也会帮助你写最后的建议。

### 由你选择的用途与方案

可以帮助维修人员预测实际故障，也可以帮助服务团队安排投诉响应，或自拟另一种有数据依据的用途。你决定将哪个结果当作要预测的标签、哪些记录还要等待、是否允许使用代理标签。不能把教学数据中的模拟真值假装成现实中随时可见的字段。

本课随附数据是教学合成数据。先读[字段和生成说明](data/DATA.md)，再查看[原始记录](data/base.json)；示例中的使用者帮助比较用途，不代表真实机构的业务。你可以全程让 AI 编写代码、计算和起草文字；不需提交完整对话。提交前要核对数字及其支持的建议。

## 本课要学会什么

- **代理标签（proxy label）**：用较易取得的记录代替真正关心的结果，需要检查二者差别。
- **延迟标签（delayed label）**：结果需要经过一段时间才能看到，未出现不等于不会出现。
- **截尾（censoring）**：观察结束时尚不知道最终结果，不能直接当作否定结果。
- **标注一致性（annotation agreement）**：不同标注者对同一记录是否判断一致，帮助发现定义不清。
- **选择偏差（selection bias）**：只有部分对象被检查或回应时，可见标签可能不能代表所有对象。

[学习材料](LEARN.md)用一个小例子解释这些概念。它们应帮助你选择和检查方案，不能只出现在报告的术语表里。

## 90 分钟安排

本课按下面的顺序进行：
- **0—15分钟辨别真实目标与代理。**
- **15—28分钟手算标签差异。**
- **28—52分钟生成与检查标签。**
- **52—65分钟比较等待和样本代价。**
- **65—75分钟重跑与建议。**
- **75—90分钟概念题与变式。**

遇到实现困难，可以让 AI提供更完整的代码，也可以复用现有程序。优先减少重复操作与排版时间，保留比较与判断。

## 完成步骤

1. 阅读 data/base.json 中关于标签与观察时间的说明，核对哪些字段只供教学对照。
2. 先预计代理标签会漏掉或误报哪些对象，再运行分析；修改 config.json 或标签生成程序时保留原始数据。
3. 在 report.md 用具体记录解释一次标签分歧，报告纳入与排除的数量及原因。

### 运行与修改

从学生仓库根目录运行：

```bash
python3 lesson-04/analysis.py
```

默认结果保存为 `lesson-04/artifacts/summary.json`。打开[配置文件](config.json)与[程序](analysis.py)，结合数据说明修改：`observation_day` 控制已经观察到哪一天，`agreement_threshold` 是提示需要进一步检查的一致性标准；它不是标签正确的保证。 默认设置仅用于开始实验，不是评分答案。需要其他模型、指标或输出时，可以替换程序，写清依赖和运行命令。

在新的输出目录再运行一次，便于比较两次结果：

```bash
python3 lesson-04/analysis.py --output artifacts/S02-demo
```

`--output` 后面是目录。报告中引用实际生成的数值，写清两次运行各用了什么设置。设计的错误输入可保存在本课目录，写明如何通过程序检查；保留原始数据副本；另存你设计的输入，说明改了哪里和为什么。

### 必做任务（Core）：把本课问题回答完整

1. 明确真正关心的结果与目前记录的结果，列出两者可能不一致的原因。
2. 根据用途选择纳入记录和标签生成规则；实际计算代理标签差异或延迟观察的影响，并写出分母。
3. 比较另一条合理的标签路线，说明样本量、等待时间与错误风险怎样变化。
4. 构造一条“还没观察到”和“确认没有”容易混淆的记录，检查流程如何处理；据此修改建议。

完成比较后，按[仓库首页](../../README.md)的环境说明在干净环境从原始数据重新运行，核对主要数值，保存实际输出。程序不能运行时记录命令、报错和已核对部分，修复后补跑；不要把估计的数字写成运行结果。

## 必须提交什么

一份标签说明、可重跑的生成或筛选流程、两条标签路线的数量与差异、一个未观察完整的案例，以及允许用于哪些对象的建议。关键是说明标签代表什么，不能只交一致率。

- [任务说明](contract.json)：用已有字段写清问题、使用者、数据、指标、划分办法和最初预计；数据不需要划分时说明原因。
- [预计与结论](report.md)：先保留预计，再写实际选择、关键结果、错误案例、修改或保留的建议。可以按自己的问题组织，引用程序产生的文件。
- 程序、配置、支持结论的结果文件，以及[提交说明](submission.json)。若更换运行入口或结果路径，同步修改提交说明；完成后把 `status` 改成 `complete`。

自动检查可以帮助发现文件、字段或路径问题。方案是否合适仍要看本课的比较与解释，检查通过不替代这些判断。

## 不同起点怎么做

### 入门支持（Support）：借助现成工具完成同一个问题

用现有标签对照表检查一种分歧和一个观察未完成案例，保留全部用途判断。

### 必做任务（Core）：完成上面的比较、检查和建议

所有人都要完成“完成步骤”中的四项判断，并交出“必须提交什么”中的具体成果。选择简单办法或有依据地暂不使用，都可以完成主任务。

### 提高任务（Upgrade）：对重要选择多做一次有用的检查

检查标签差异是否集中在某一类对象，评价统一处理是否合适。

### 换数据重测（Transfer）：换一份数据或场景再跑一次

换成不同观察时长或不同群体，再运行标签流程。

### 自选拓展（Open extension）：提出本课问题之外的新探索

设计一份小型标注说明，让另一人或AI按说明解释边缘案例。

## 运行限制

随课示例包含 180 条记录，数据文件约 52.7 KB。自带数据时先取能说明问题的小样本，建议不超过 100 MB，再按下面的时间目标控制实验规模。

必做部分使用本地数据、普通CPU和约8 GB可用内存，不需要GPU、网络下载或付费API。保留小数据和小模型；单次运行目标不超过3分钟，从原始数据重新运行目标不超过5分钟。新增依赖写入环境说明，课前准备好离线安装材料。更多数据、更大模型或联网服务可用于自选拓展，但必须有能离线完成必做判断的版本。

时间和资源要求是课程设计目标，真实耗时以你的记录为准。超出限制时先减少无关搜索、重复运行或模型规模，保留关键比较；不要省略需要解释的错误。
