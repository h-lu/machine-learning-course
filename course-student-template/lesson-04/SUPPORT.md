# S02 入门支持：这八条标签，哪些能直接用于统计

这是 [本课任务](README.md) 的详细路径，不是额外作业。你不需要先写训练代码。**第一项小任务：找到第 4 天已收到的四条标签，算出它们的平均值。**然后才看另一份标注和缺失记录。

## 1. 先准备一句话和一个文件

在学生仓库根目录操作，那里同时有 `scripts` 和 `lesson-04`。不清楚终端在哪里时，按 [第一次运行指南](../docs/FIRST_RUN.md) 检查；不要把命令输进 Python 的 `>>>`。只能识别 `python3` 的电脑，将下面的 `python` 换为 `python3`。

先打开 `report.md`，写：“本次检查 A、B 窗口第 1–4 天已经发生的八条排队记录，统计实际等待，不把估计值当实际记录。”然后用自己的话写一个预计，例如截止日推迟后可能多收到哪些标签。只先写这一段，其余等运行后填写。

先读 [LEARN.md](LEARN.md) 的第 1–3 节。本课**目标值**是实际等待分钟数；**代理标签**是替代估计；**缺失标签**是尚未收到的实际记录。`day` 是发生日，`available_day` 是上传日，日期不是等待分钟数。


先只找 `id`（编号）、`visible`（标签是否已收到）、`observed_minutes`（可用的实际记录）。`True` 表示是，`False` 表示否；空白不是 0。八行对应八条经历，不能先删除未知行再算覆盖率。

## 3. 停下来手算，并说明每个分母

只取 `visible=True` 的 A01、A02、A04、B02。用下面小表核对，软件故障时也可先在纸上完成：

| 编号 | 可用实际记录（分钟） | 代理估计（分钟） | 第二份标注（分钟） |
|---|---:|---:|---:|
| A01 | 1 | 1 | 1 |
| A02 | 3 | 3 | 3 |
| A04 | 7 | 7 | 10 |
| B02 | 9 | 5 | 9 |

先算四个实际值的均值，再算“有标签记录数 ÷ 全部记录数”。打开同目录 `comparison.csv`，在 `method=available_only` 行核对 `n`、`mean_minutes`、`coverage`。

接着比较 A04 的 `observed_minutes` 和 `review_minutes`。`review_absolute_difference` 是两数的绝对差，`disagreement=True` 表示超过容差。默认容差为 2 分钟，“超过”不包含等号。另看 B02 的 `proxy_absolute_error`：这里比较的是代理估计与实际参照，不是两份标注的一致性。

<details>
<summary>先自己算，再展开核对起点</summary>

实际记录之和是 20，均值 `20/4=5` 分钟；覆盖率 `4/8=50%`，程序以 0.5 保存。A04 两份数相差 3 分钟，所以四对中一对有分歧，一致比例 `(4-1)/4=75%`。B02 的代理误差为 `|5-9|=4`，四条的代理 MAE 为 `(0+0+0+4)/4=1` 分钟。

`zero_fill_demo` 行错误地加入四个 0，得到 2.5 分钟；`proxy_all` 行平均的是八个代理估计，得到 4 分钟。它们均不等于八条经历的实际平均等待。其他行空着的覆盖率不是 0，也不是 100%。

</details>

自查数值只对应给定数据和配置，不是评分目标。数对不上时，先检查方法、列名、配置和输出目录，不手改表格。

## 4. 只改观察日期：为什么均值变了

运行前先写：把截止日从第 4 天改为第 7 天，会改变已经发生的等待，还是只改变已收到的标签？

`config-support.json` 已准备好，只改 `observation_day=7`，`later_day` 仍为 7。运行：

```bash
python lesson-04/analysis.py --config lesson-04/config-support.json --output lesson-04/artifacts/support-compare
```

把两次 `records.csv` 并排，找从 False 变成 True 的编号，核对日期。A04 在第 4 天当天上传，起点就可见；A03 第 6 天上传，起点不可见。别从原数据文件抄未来标签来填写起点。

<details>
<summary>日期对照的核对结果</summary>

新增收到 A03、B01、B03，总数仍为八条。七个已知值之和为 43，均值 `43/7≈6.143` 分钟，覆盖率 `7/8=87.5%`。B04 在本材料中仍未知。前后不是两批不同日期的服务记录，不能说等待因此变长。

</details>

`summary.json` 的 `stress_test.metrics` 会额外报告 `later_day` 的情况。它只是同一批标签的另一截止日；当两个日期都为 7 时，统计相同是正常的，并非程序未生效。

## 5. 做一次自己的检查，再提出复核计划

从 `config-start.json` 另存为 `lesson-04/config-mine.json`，不要从第 7 天的对照复制。最简单的个人检查是保持第 4 天，只改 `disagreement_minutes`，例如 1 或 3 分钟。先写为什么想检查这个值，以及预计 A04 的分歧标记是否改变。也可以选择一个有理由的观察日期，但每次只改一项。

保留原来的四个字段及英文标点，不要让文件名多出 `.txt`；再检查格式并运行：

```bash
python -m json.tool lesson-04/config-mine.json
python lesson-04/analysis.py --config lesson-04/config-mine.json --output lesson-04/artifacts/my-check
```

先看终端的配对数量、分歧数量、一致比例，再看 A04 的两个原值。改容差不会改原值、覆盖率或代理 MAE。如果选 3，差异恰好为 3 不算超过；如果结果没有变化，也解释为什么。

在报告写出一条具体复核计划：例如先查 A04 的开始／结束计时记录，或联系 B04 的记录者补充标签。说明这只是计划，程序没有真的联系人员或修改标签。不能仅靠提高一致比例认定标签变准确。

需要 AI 帮助时，可以给它一行数据，要求先解释“正在比较哪两个数、分母是什么”，等你作答后再核对，不要让它代填最终建议。
