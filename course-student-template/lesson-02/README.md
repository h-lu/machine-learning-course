# C02 · 一个分数够不够支持使用

## 本课要解决什么问题

上一课你学会了让别人重新算出一次预测。本课进一步问：一个办法的分数看起来不错，是否真的足以支持使用？

假设一个值班小组每天只能复核 5 条记录。一个预测办法每天挑出 20 条，其中 8 条确实值得复核。它可能比另一个办法更容易找到目标，也可能让工作人员面对太多无用记录。只看一个总体分数，不能回答“谁会被漏掉”“每天要处理多少条”“这个办法是否比最简单的办法更有帮助”。

你会比较两种办法：

- **简单起点**：用训练资料中目标值的平均数，给每条新记录同一个预测；
- **候选办法**：只使用一列输入，拟合一条直线，再给出预测。

这里的“候选办法”只是课堂中的小实验，不是让你承诺上线。你要先写清楚使用者关心什么，再用同一批评价资料比较两种办法，检查一个重要的小组或错误情形，最后决定继续试用、保留简单起点、修改方案，还是暂时不用。

本课数据也是为了教学生成的合成数据。它不代表真实机构，也不能支持对真实人群的结论。你可以全程使用 AI 帮你写代码、计算和组织文字，但必须自己核对数字、分母和建议。

## 本课要学会什么

- **训练资料和评价资料**：训练资料用来形成预测办法；评价资料只用来检查办法面对新记录时的表现。两种办法必须面对同一批评价资料，比较才公平。
- **简单起点（baseline）**：一个不追随复杂关系的办法，例如总是预测训练资料的平均值。它告诉你候选办法是否真的增加了帮助。
- **评价指标（metric）**：把预测和实际结果比较的数字。指标不是越高越好：先说明它的单位、分母，以及哪种错误更需要关注。
- **平均绝对误差（MAE）**：每条记录先算“预测和实际相差多少”，再取平均。它和结果使用相同单位，比较容易解释。
- **分组检查**：把有实际意义的一组记录单独拿出来看，防止平均值掩盖重要错误。

先读[学习材料](LEARN.md)，再运行程序。学习材料会说明为什么“总体平均误差更小”仍然可能不是好消息。

## 90 分钟安排

- **0–15 分钟：先定使用目标。** 写下谁会使用预测、结果出来后要做什么，以及最不能接受哪一种错误。
- **15–30 分钟：看一个小例子。** 手算简单起点和候选办法的误差，先写下预计哪一种会更好、为什么。
- **30–50 分钟：运行比较。** 运行程序，确认两种办法用了相同的评价记录，记录 MAE、RMSE 和记录数。
- **50–65 分钟：检查一个重要分组。** 选择一个和用途有关的分组，查看总体结果是否掩盖了某类记录的较大错误。
- **65–75 分钟：设计条件变化。** 改变一项输入条件或加入一条容易出错的记录，观察建议是否需要修改。
- **75–90 分钟：学习和提交。** 完成 `ml-check` 的本课 A 版、AI 学习和 B 版，整理报告和结果文件。

可以请 AI 解释公式或协助修改程序。请先写自己的预计，再运行和核对；不要用 AI 事后编出的理由代替实际比较。

## 完成步骤

### 1. 先写“好不好”是什么意思

打开[字段和生成说明](data/DATA.md)、[原始记录](data/base.json)、[任务说明](contract.json)和[报告](report.md)。在 `contract.json` 中填写：

- `question`：你要支持哪一个决定？例如是否继续试用候选办法。
- `user`：谁会使用预测，能处理多少条记录？
- `data_source`：数据从哪里来，一行记录代表什么，哪些结果已经知道？
- `metric`：你选择 MAE、RMSE 或其他检查数字的原因；写清单位和分母。
- `split_plan`：哪些记录用于形成办法，哪些记录留到最后比较；不能让两种办法使用不同的评价记录。
- `initial_expectation`：运行前写下你预计的排名、误差和可能失败的小组。

如果使用者只能处理固定数量的记录，也要把这个限制写进 `question` 或 `metric`。分数必须能帮助使用者做决定。

### 2. 运行默认比较

```bash
python3 lesson-02/analysis.py
```

结果默认写入 `lesson-02/artifacts/summary.json`。打开文件，先确认：

- `config.feature`：候选办法使用的是 `x1` 还是 `x2`；
- `metrics`：候选办法在评价资料上的误差；
- `comparison.training_mean`：简单起点在同一评价资料上的误差；
- `stress_test`：输入整体改变后，误差怎样变化；
- `provenance`：数据、配置和程序版本，方便别人重新运行。

结果中的 `n` 是实际参与评价的记录数。比较 MAE 时，两种办法的 `n` 应相同；如果不相同，先找出原因，不要直接比较小数。

### 3. 追一条记录，再看一个分组

从结果的 `details` 中选一条记录，写出输入值、实际结果、两种预测和各自误差。然后选择一个和用途有关的分组，例如 `group` 或 `user`，说明：

- 这个分组为什么和使用有关；
- 该组有多少条记录；
- 候选办法和简单起点在该组的表现是否仍按同一标准计算；
- 这个结果会不会改变你的建议。

不要为了让候选办法看起来更好而随意挑分组。若分组只有一两条记录，要明确写出这个数量很少，不能把它说成普遍规律。

### 4. 设计条件变化并重新运行

默认程序把评价资料中的特征整体增加 2，检查输入条件改变时误差是否明显增加。你可以修改 `config.json` 中的 `feature`，或在程序中加入一条有理由的测试记录。

```bash
python3 lesson-02/analysis.py --output artifacts/C02-demo
```

比较原始运行和新运行，写清楚改了什么、为什么改、哪个数字改变，以及你的使用建议是否改变。不要覆盖原始结果。

### 5. 完成必做任务（Core）

1. 先写使用目标、接受标准和预计结果。
2. 用相同的评价资料比较简单起点和候选办法。
3. 检查一个有实际理由的分组或错误情形，并同时写出记录数。
4. 根据总体结果、分组结果和条件变化，决定继续试用候选办法、保留简单起点、修改方案或暂时不用。
5. 在新的输出目录重新运行，确认主要数字仍能由程序产生。

最后按[仓库首页的环境说明](../../README.md)在干净环境重新运行。报告中只能写实际运行得到的数字；程序失败时保留命令、报错和已经核对的部分。

## 必须提交什么

请提交以下内容：

- `contract.json`：填写好的使用目标、使用者、数据、检查数字、资料划分和预计结果；
- `report.md`：两种办法的比较、一个分组检查、一条错误记录或条件变化、第一次建议和最后建议；
- `analysis.py`、`config.json`：实际运行的程序和设置；
- `artifacts/` 中的比较结果和新运行结果；
- `submission.json`：报告路径、结果路径和运行命令，并把 `status` 改为 `complete`。

合格的作品不要求候选办法胜出。只要比较条件相同，结果可重新计算，建议能用证据解释，保留简单起点或暂时不用都可以。自动检查只检查文件、字段和路径，不能替你选择模型。

## 不同起点怎么做

### 入门支持（Support）：先学会读两个结果

直接运行默认程序，找出两种办法的 `n`、MAE 和 RMSE。手算一条记录的误差，再检查一个分组。可以请 AI 解释平均绝对误差，但要用自己的话写出分母是什么。

### 必做任务（Core）：完成一次公平比较

完成“完成步骤”中的五件事：先写目标，比较两种办法，检查分组或错误，改变条件后重跑，再修改建议。候选办法没有胜出也可以完成。

### 提高任务（Upgrade）：检查结论是否稳定

换一个合理的输入列或重新设计一个评价分组，保持评价方法不变，说明排名是否改变以及为什么。

### 换数据重测（Transfer）：换一份数据或场景再跑一次

换一份含义相同的新记录，重新计算两种办法。说明数据构成变化是否影响总体结果和分组结果。

### 自选拓展（Open extension）：为另一种行动重新评价

把预测用于不同的行动，例如“减少平均误差”和“尽量避免大错”。重新说明什么结果算可接受，并解释评价标准为什么变化。

本课数据约 180 行、文件约 40 KB。必做任务只使用仓库内的离线数据、普通 CPU 和约 8 GB 可用内存，不需要 GPU、网络下载或付费 API。单次运行目标不超过 3 分钟，从原始数据重新运行目标不超过 5 分钟。

如果替换数据或增加依赖，请在报告中写明数据怎样得到、每行代表什么、依赖怎样安装，并保留一个不需要联网的必做版本。数据只是教学样例，不能据此声称真实机构或真实人群的表现。
