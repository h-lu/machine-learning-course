# S29｜模型运行后，什么时候需要处理

## 本课要解决什么问题

为一个已运行的模型设计监控与处理办法，例如让值班人员检查图书需求预测何时不再适合安排准备量；也可以复用自己的项目。判断输入改变、错误增多和资料缺失分别意味着什么。你要决定出现什么证据后继续使用、转人工或恢复旧版本。提交批次检查、一次故障演练和处理说明。没有真实标签时先承认无法直接判断准确性，不把输入分布变化自动当作模型失效。

起步程序使用合成表格中的线性模型，比较新批次误差与输入变化，并运行缺字段请求。默认阈值只作示例，不能直接当作你的使用标准；合成字段没有真实业务单位，要先说明如何解释或换成自己的数据。

数据字段和生成方式见 [数据说明](data/DATA.md)。你可以改问题、数据、方法和评价；必须说明至少一个选择怎样影响结果。示例的结论不是你的任务答案。

## 本课要学会什么

- **输入接口约定（input schema）**：明确字段、类型和允许值，在计算前发现无法处理的输入。
- **数据漂移（data drift）**：新输入分布与参考时期不同，它提示需要检查，但不必然说明性能下降。
- **性能监控与标签延迟（performance monitoring / label delay）**：有结果标签后才能直接核对误差；没有标签时只能用有限信号。
- **触发标准与恢复旧版本（alert threshold / rollback）**：把监控信号连接到明确处理动作，避免只画图无人处理。

读 [学习卡](LEARN.md)，先用里面的小例子理解计算，再决定本课实验怎样用这些概念。

## 90 分钟安排

| 时间 | 你要做什么 |
|---|---|
| 0–12 分钟 | 确定使用者和问题，写下预计会看到的结果 |
| 12–25 分钟 | 学习本课概念，核对学习卡的一处计算 |
| 25–52 分钟 | 用 AI 协助运行起点并实现自己的比较 |
| 52–65 分钟 | 核对主要数字，运行自己设计的失败或条件变化检查 |
| 65–75 分钟 | 在新输出目录重跑，写出结论并整理提交 |
| 75–90 分钟 | 先做概念检查，再用 AI 学习，最后判断一个不同情境 |

新环境在课前准备；课堂内留时间复跑。遇到技术故障，先保留错误信息，按 [故障处理](../../docs/TROUBLESHOOTING.md) 修复，并说明还有哪一步没有完成。

## 完成步骤

下面命令从学生仓库根目录运行。没有安装环境时，先按 [环境准备](../../docs/GETTING_STARTED.md) 完成准备。

1. **把问题写具体。** 选择一个具体预测用途和接收结果的人，定义哪些错误后果不可接受。说明真实标签多久可得到、谁会查看信号，以及出现问题后能用什么旧方案或人工流程。 在 `contract.json` 中填写任务说明（task specification）：问题、使用者、数据来源、主指标、评测划分与预计结果。先写下预计会看到的结果，再开始比较。
2. **读数据并运行起点。** 先读本课 `data/DATA.md` 和 `config.json`，确认每条记录及参数的含义；运行后打开生成的 `summary.json`，区分示例结果与自己的结论。

   ```bash
   python3 lessons/S29/analysis.py
   cp lessons/S29/config.json lessons/S29/config-trial.json
   cp lessons/S29/data/base.json lessons/S29/data/trial.json
   ```

3. **做出有理由的比较。** 保留一个参考批次，在新批次分别检查输入完整性、输入分布和有标签时的误差。比较两种有依据的触发标准或处理方式；阈值应来自允许后果、复核容量或历史波动。 可以让 AI 解释、修改代码并整理图表；在配置和数据副本中完成自己的改动，保留原始文件。若新任务超出接口，直接改写 `analysis.py`，并记录新的运行命令。

   ```bash
   python3 lessons/S29/analysis.py --config lessons/S29/config-trial.json --data lessons/S29/data/trial.json --output lessons/S29/artifacts/trial
   ```

4. **核对数字和含义。** 核对每个指标的时间段和分母，区分缺标签与错误为零。把输入变化但误差稳定、输入相近但误差变差两种情况分开讨论；不要只检查总体平均而忽略受影响群体。 不只复制汇总结果，要追踪至少一个样本、计数或计算过程。
5. **加入自己的检查。** 自己构造一个实际故障，例如必需字段缺失、某一组偏差突然变大或标签迟到。运行检查并沿你写的流程走一次，记录是否暂停预测、转人工或恢复旧方案。 起步程序已有的条件变化帮助理解方法，但还需要你提出并实际运行一条与自己用途有关的检查；保留它支持或推翻原判断的结果。
6. **修改决定并重跑。** 列出监控信号、参考时期、触发标准和具体处理；给出正常与异常批次计数、失败演练和恢复条件；根据证据决定继续、限制或停止使用。 把说明写进 `update.md`，比较实际结果与原先预计。在课前准备的新环境或干净仓库副本中运行下面命令，确认程序不依赖旧输出；若尚未完成新环境验证，如实写出已验证到哪一步。

   ```bash
   python3 lessons/S29/analysis.py --config lessons/S29/config-trial.json --data lessons/S29/data/trial.json --output /tmp/ml-s29-recheck
   ```

   核对主要数字后，将最终结果留在仓库内，并更新 `submission.json` 的进度、运行命令和文件位置。它是提交清单；具体字段和正式结果保存办法见 [提交说明](../../docs/SUBMISSION.md)。

## 必须提交什么

- 程序、实际使用的数据或获取说明、参数与运行命令，让别人能重新得到主要结果。
- 写明用途与预计结果的 `contract.json`，以及包含主要指标和分母的程序输出。自己的结果不能只保留默认示例。
- 自己设计并实际运行的失败输入或条件变化、输出和解释；可引用单独文件，不要求固定图表数量。
- `update.md` 中的比较、与预计不同之处，以及采用、限制试用或停止使用的理由；`submission.json` 指向最终文件。

有依据地不采用模型可以完成本课。仍需提交已运行的比较、失败证据和可行的下一步，不能用“效果不好”替代分析。

## 不同起点怎么做

### 必做任务（Core）：完成所有人都要作出的关键判断

检查输入、分布与误差三类信号；说明标签未到时的限制；比较处理标准；实际运行一个故障并演练对应动作；从新目录重跑且保留旧方案说明。

### 入门支持（Support）：用较小的起点完成同样的判断

先从缺字段和有标签批次的平均绝对误差开始；AI 可生成监控汇总，你要明确触发后谁做什么。

### 提高任务（Upgrade）：增加一种能改变判断的比较

加入分组、时间窗口、持续超标或成本预算，研究减少误报会不会延误真实故障处理。

### 换数据重测（Transfer）：换一份数据或场景再跑一次

换一个标签延迟或人群组成不同的场景再跑一次，重新确定参考批次和处理标准。

### 自选拓展（Open extension）：课后探索自己提出的新问题

可以沿本课问题尝试更大数据、其他模型或已有服务。先写它比必做实验多回答什么，再报告实际资源与新增证据；未运行的能力写成待验证假设。

## 运行限制

必做只读取离线合成批次，不连接线上服务；每个批次不超过 10,000 行。 默认普通 CPU、约 8 GB 可用内存即可，课堂实验离线运行，不依赖付费 API、云 GPU 或临时下载大模型。单次目标不超过 3 分钟，从头重新运行目标不超过 5 分钟。超过预算时先缩小数据或重复次数，保留本课必须完成的比较与判断，并记录缩减影响。

所有起步数据都是教学合成数据或人工微型样例，不能当作真实机构、真实群体或实际线上效果。参数和输出接口见 [运行办法](../../docs/RUNTIME.md)。
