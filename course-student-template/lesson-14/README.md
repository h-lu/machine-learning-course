# 第 14 课 · 没有故障标签，先检查哪些记录

## 本课要解决什么问题

巡检小组没有完整故障标签，却有一批多项测量。每天只能人工查看少数记录，希望发现数据问题或值得进一步了解的异常。你要建立一份可解释的检查队列，说明分数为什么高以及查看后能做什么。

请交排序程序、检查名单、人工容量与案例说明。高分记录可能只是少见而合理；确认不了故障时，报告需要补什么数据，不把“异常”直接写成“错误”。

开始前先写清楚四句话：谁会使用结果？输入在什么时候能得到？程序输出什么？结果变差时怎么办？这四句话会帮助你选择评价方法，也会帮助你写最后的建议。

### 由你选择的用途与方案

可以帮助数据人员找测量问题，也可以帮助维修人员寻找偏离常见模式的设备；可自拟用途。由你选择缩放、保留维数、异常分数与检查名额。是否把远离中心、偏离相关关系或规则违规列为优先，要依据用途决定。

本课随附数据是教学合成数据。先读[字段和生成说明](data/DATA.md)，再查看[原始记录](data/base.json)；示例中的使用者帮助比较用途，不代表真实机构的业务。你可以全程让 AI 编写代码、计算和起草文字；不需提交完整对话。提交前要核对数字及其支持的建议。

## 本课要学会什么

- **主成分分析（PCA）**：寻找数据变化较大的方向，用较少维度表示原始记录。
- **解释方差（explained variance）**：说明保留了多少数值变化，不直接说明保留了多少任务信息。
- **重构误差（reconstruction error）**：比较原记录与低维表示还原后的差别，用来寻找偏离常见关系的记录。
- **异常分数（anomaly score）**：表达某种偏离程度，方向与单位需说明。
- **人工容量（review capacity）**：把分数转为可处理的队列，还要考虑检查后怎样确认。

[学习材料](LEARN.md)用一个小例子解释这些概念。它们应帮助你选择和检查方案，不能只出现在报告的术语表里。

## 90 分钟安排

本课按下面的顺序进行：
- **0—13分钟确定检查目的。**
- **13—28分钟手算投影例子。**
- **28—52分钟比较队列。**
- **52—66分钟核查高分与遗漏。**
- **66—75分钟建议与重跑。**
- **75—90分钟概念题与变式。**

遇到实现困难，可以让 AI提供更完整的代码，也可以复用现有程序。优先减少重复操作与排版时间，保留比较与判断。

## 完成步骤

1. 先在 report.md 预计远离中心与偏离相关关系会找出同样还是不同记录。
2. 修改 config.json 的 components或review_capacity，运行实验并对照原始输入查看名单。
3. 从最高分之外寻找一条可能重要的记录，检查当前分数没有表达什么。

### 运行与修改

从学生仓库根目录运行：

```bash
python3 lesson-14/analysis.py
```

默认结果保存为 `lesson-14/artifacts/summary.json`。打开[配置文件](config.json)与[程序](analysis.py)，结合数据说明修改：`components` 控制保留维数，`review_capacity` 控制人工检查数量。 默认设置仅用于开始实验，不是评分答案。需要其他模型、指标或输出时，可以替换程序，写清依赖和运行命令。

在新的输出目录再运行一次，便于比较两次结果：

```bash
python3 lesson-14/analysis.py --output artifacts/S12-demo
```

`--output` 后面是目录。报告中引用实际生成的数值，写清两次运行各用了什么设置。设计的错误输入可保存在本课目录，写明如何通过程序检查；保留原始数据副本；另存你设计的输入，说明改了哪里和为什么。

### 必做任务（Core）：把本课问题回答完整

1. 确定检查目的与名额，说明什么证据能够确认问题，什么只能提出疑点。
2. 比较低维重构分数与一种简单偏离或规则分数，核对主要维度、人数和实际名单。
3. 检查保留维数或缩放改变后，优先名单如何变化；说明变化对用途的意义。
4. 选一条高分但可能合理的记录，以及一条可能被遗漏的输入，决定如何补证据和修订队列。

完成比较后，按[仓库首页](../../README.md)的环境说明在干净环境从原始数据重新运行，核对主要数值，保存实际输出。程序不能运行时记录命令、报错和已核对部分，修复后补跑；不要把估计的数字写成运行结果。

## 必须提交什么

可重跑的两种队列比较；维数与容量选择；两条需要不同解释的案例；人工核查步骤和采用建议。合格标准是区分可疑与已确认，并说明队列遗漏的可能性。

- [任务说明](contract.json)：用已有字段写清问题、使用者、数据、指标、划分办法和最初预计；数据不需要划分时说明原因。
- [预计与结论](report.md)：先保留预计，再写实际选择、关键结果、错误案例、修改或保留的建议。可以按自己的问题组织，引用程序产生的文件。
- 程序、配置、支持结论的结果文件，以及[提交说明](submission.json)。若更换运行入口或结果路径，同步修改提交说明；完成后把 `status` 改成 `complete`。

自动检查可以帮助发现文件、字段或路径问题。方案是否合适仍要看本课的比较与解释，检查通过不替代这些判断。

## 不同起点怎么做

### 入门支持（Support）：借助现成工具完成同一个问题

使用已有PCA结果与简单分数，重点检查名单差异和两条案例。

### 必做任务（Core）：完成上面的比较、检查和建议

所有人都要完成“完成步骤”中的四项判断，并交出“必须提交什么”中的具体成果。选择简单办法或有依据地暂不使用，都可以完成主任务。

### 提高任务（Upgrade）：对重要选择多做一次有用的检查

比较不同维数和尺度，评价名单稳定性与可解释性。

### 换数据重测（Transfer）：换一份数据或场景再跑一次

换成传感器范围或相关关系变化的数据，重新检查分数含义。

### 自选拓展（Open extension）：提出本课问题之外的新探索

设计少量人工核查记录表，研究核查信息怎样改进下一轮队列。

## 运行限制

随课示例包含 180 条记录，数据文件约 39.6 KB。自带数据时先取能说明问题的小样本，建议不超过 100 MB，再按下面的时间目标控制实验规模。

必做部分使用本地数据、普通CPU和约8 GB可用内存，不需要GPU、网络下载或付费API。保留小数据和小模型；单次运行目标不超过3分钟，从原始数据重新运行目标不超过5分钟。新增依赖写入环境说明，课前准备好离线安装材料。更多数据、更大模型或联网服务可用于自选拓展，但必须有能离线完成必做判断的版本。

时间和资源要求是课程设计目标，真实耗时以你的记录为准。超出限制时先减少无关搜索、重复运行或模型规模，保留关键比较；不要省略需要解释的错误。
