# S24 教师运行单：怎样用下一项实验改进整件作品

状态：已随 `ml-v13-course-map-2026-09-21` 于 2026-09-21 发布；本次没有真人 90 分钟试读。学生目录为 `lesson-26`。

## 主要关系与前置知识

主要关系是：先用开发证据选择一项修改，固定候选后，再用没有参与选择的 holdout 做一次最终评价。前置为 S19–S23 的完整作品、公平比较、开发与最终评价的区别。

原方案来自本模块给定且实际运行的流程。默认候选只改变 `filter_untrusted`。W01–W12（包括后半 W07–W12）都已经是开发证据；F01–F06 才是单独 holdout。自动处理、自动错误、适当转人工和不必要转人工必须分别报告。

## 最小资源与课前准备

课前先运行两个 development 配置，确认只产生 `development_cases.csv`；再在独立目录用 `config-final.json` 与 `data/holdout.json` 运行，确认只产生 `final_cases.csv`。development 配置配 holdout、final 配置配开发数据都应报错。模板 `submission.json` 默认仍是 development；学生固定候选并实际运行 final 后，才复制 `submission-final.json`，避免平时执行 `scripts/course.py run 26` 时静默读取 holdout。

公开学生仓库无法从技术上阻止提前打开 holdout。课堂要执行操作顺序：学生先提交或记录固定配置，再由教师允许执行 final。高风险正式评价应由教师在固定配置后另发未公开数据。

## 90 分钟组织

- 0–15 分钟：回顾前五课，列两个竞争解释。
- 15–35 分钟：在 W01–W12 比较无修改与来源过滤，追踪 W11。
- 35–52 分钟：学生增加一条开发条件并决定候选。
- 52–60 分钟：固定 `config-final.json`，核对只改一项。
- 60–70 分钟：单独运行 F01–F06。
- 70–78 分钟：分开核算自动结果和人工量，作出决定。
- 78–90 分钟：概念检查和提交。

## 巡视问题与失败支持

问“W07–W12 为什么不能叫最终数据”“候选是否在看 F 结果前固定”“转人工的真实结果是否观察到”“除了目标设置还有什么变化”。若学生已看 holdout 后继续调参，诚实把它改称开发证据；新的最终结论需要另备数据。

## 课堂证据

一份实际原方案、一项单因素候选、12 条开发结果、一条自拟开发条件、固定候选记录、6 条独立 holdout 结果，以及按自动处理与转人工分开的建议。候选可以胜出、持平或被放弃。
